# Реконструкция — Закрытие

Веб-приложение для управления закрытиями, реконструкциями и открытиями магазинов: календарь событий, этапы работ, справочники, уведомления и аудит.

## Стек и инфраструктура

- Frontend: React 18, TypeScript, Vite, Tailwind CSS, Zustand.
- Backend: NestJS, Prisma, PostgreSQL.
- Docker Compose: `migrate` применяет миграции и выполняет первичную настройку; `backend` обслуживает API и фоновые задачи; `frontend` раздаёт интерфейс через Nginx и проксирует `/api`.
- PostgreSQL используется внешний; контейнера базы данных в Compose нет.
- Интерфейс доступен на порту **5001**. Порт backend **4000** доступен только внутри Docker-сети.

Нужны Docker с Compose v2 и доступная из контейнеров PostgreSQL. Node.js и зависимости устанавливаются при сборке образов.

## Первый запуск

### Конфигурация

```bash
cp .env.example .env
```

Заполните `.env`:

| Переменная | Назначение |
|---|---|
| `DB_HOST`, `DB_PORT` | Адрес PostgreSQL; порт обычно `5432` |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD` | База, пользователь и пароль |
| `JWT_SECRET` | Случайный секрет не короче 32 символов |
| `JWT_EXPIRES_IN` | Срок сессии, например `15m` или `1h` |
| `DOMAIN` | Адрес интерфейса для CORS, например `http://your-server-ip:5001` |
| `LDAP_ENCRYPTION_KEY` | Постоянный ключ шифрования секретов LDAP и интеграций |
| `SCHEDULER_TIMEZONE` | Часовой пояс синхронизации магазинов; по умолчанию `Europe/Moscow` |

Генерация значений:

```bash
openssl rand -base64 48  # JWT_SECRET
openssl rand -hex 32    # LDAP_ENCRYPTION_KEY
```

`LDAP_ENCRYPTION_KEY` добавляется в `.env` при настройке LDAP или интеграций. Сохраняйте его вместе с резервной копией конфигурации: замена ключа сделает ранее зашифрованные секреты нечитаемыми.

Backend слушает фиксированный порт `4000` в текущем Compose. Значения `API_PORT` и `NODE_ENV` из примера не меняют этот порт и производственный режим контейнера. SMTP настраивается в интерфейсе; SMTP-переменные в `.env` не нужны.

### База данных и запуск

Заранее создайте базу PostgreSQL и выдайте пользователю приложения права на создание и изменение её таблиц. Compose формирует `DATABASE_URL` из `.env` автоматически.

Для новой базы передайте пароль первого администратора через окружение оболочки:

```bash
read -r -s -p 'Пароль первого администратора (12–128 символов): ' BOOTSTRAP_ADMIN_PASSWORD
printf '\n'
export BOOTSTRAP_ADMIN_PASSWORD
docker compose up --build -d
unset BOOTSTRAP_ADMIN_PASSWORD
docker compose rm -f migrate
```

Логин первого администратора — `admin`. Пароль вводится командой выше и не сохраняется в `.env`. Удаление завершённого контейнера `migrate` убирает его копию из окружения контейнера.

Если пароль первичной настройки не задан, текущий seed создаёт отсутствующую учётную запись `admin` с паролем `admin123`. Для новой установки задавайте собственный пароль. Пароль существующего администратора при обычном запуске не сбрасывается.

После запуска:

- Интерфейс: `http://your-server-ip:5001`.
- Проверка API: `http://your-server-ip:5001/api/health`.
- Swagger отключён; `/api/docs` возвращает `404`.

```bash
docker compose ps
docker compose logs --tail=100 migrate backend frontend
```

Завершение `migrate` с кодом `0` нормально. Backend запускается после успешной миграции, frontend — после проверки здоровья backend.

### Объекты и этапы

- Типы работ: закрытие, реконструкция, открытие.
- Номер магазина выбирается из справочника; адрес подставляется автоматически.
- ТУ выбирается через поиск; в новом событии по умолчанию не выбран.
- Этапы содержат контрольные даты и задачи. Выполненные задачи сохраняют исполнителя и время изменения.
- В автоматическом режиме статус определяется датами и выполнением этапов.
- При ручном статусе отметки задач блокируются, подсказка «Через N дн.» скрывается. Для изменения отметок нужно включить автоматический режим и сохранить карточку.
- Результат создания заявки SD и её номер сохраняются сервером и отображаются у задачи «Заявка в SD создана». Остальные задачи не перезаписывают номер SD.
- Доступны комментарии, история изменений, цвет строки и экспорт при наличии соответствующих прав.

### Профиль и роли

Личный профиль позволяет изменить имя, логин и пароль. Тема выбирается иконкой рядом с кнопкой аккаунта в верхней панели: светлая, тёмная или системная. Выбор сразу сохраняется в PostgreSQL.

Роли разделяют просмотр и действия; управление объектами проверяется отдельно для закрытий/реконструкций и открытий. Выбор действия в форме роли включает право просмотра раздела. Права уведомлений находятся в группе «Настройки». Права удаления комментариев нет.

Сессия завершается по сроку JWT. Профиль и права периодически обновляются без повторного входа. Справочники загружаются по потребностям открытого раздела; профиль не вызывает общую загрузку справочников.

### Аудит

Журнал содержит автора, время и содержание изменения. Имя автора определяется через связь с `users`; столбца `userName` в `audit_logs` нет. Удаление записей защищено на уровне PostgreSQL; очистка доступна отдельным действием с соответствующим правом.

Изменения личного профиля, темы и пароля через `/auth/me/*` не добавляются в аудит. Старые API-события изменения профиля скрываются из выдачи.

Для новых ошибок сохраняется причина: сообщение API, ошибки проверки полей или причина сбоя сервиса. Причина отображается в строке события и раскрытых деталях. Для старых записей без причины показывается пояснение; неизвестная причина не восстанавливается предположениями. Пароли и ключи скрываются в сохраняемых данных запроса.

## Справочники и интеграции

### Магазины: SQL Server

Источник по умолчанию — представление `Ukm_Data.dbo.v_1C_Shops_Info`. В `.env` задаются:

```env
UKM_SQL_SERVER=your-sql-server-host
UKM_SQL_PORT=1433
UKM_SQL_DATABASE=Ukm_Data
UKM_SQL_USER=your_readonly_user
UKM_SQL_PASSWORD=change_me
UKM_SQL_VIEW=[Ukm_Data].[dbo].[v_1C_Shops_Info]
```

Backend включает Python, pyodbc и Microsoft ODBC Driver for SQL Server. При синхронизации магазины добавляются или обновляются; отсутствующие в источнике записи не удаляются. Ручной запуск доступен в справочнике при наличии `manage_shops`.

### ТУ: Active Directory

Подключение LDAP задаётся в `/settings/ldap`, синхронизация ТУ запускается из справочника ТУ. Для хранения пароля подключения нужен `LDAP_ENCRYPTION_KEY`. Отключённые ТУ недоступны для новых назначений.

### Уведомления

IntraDesk, Пачка и SMTP настраиваются в `/settings/integrations`; правила — в `/settings/notifications`. Секреты хранятся в базе зашифрованными.

Правило задаёт событие, число календарных или рабочих дней до него, время, канал и шаблон сообщения. Подстановки: `{shopNumber}`, `{address}`, `{tuFio}`, `{tuPhone}`, `{closureDate}`, `{demolitionDate}`, `{installationDate}`, `{techOpenDate}`.

Проверка отправок выполняется каждые 10 секунд по `Europe/Moscow`. Статус отправки и номер/ID сохраняются в `notification_deliveries`. Правило IntraDesk за один рабочий день до закрытия также сохраняет результат в задаче `sdRequest` объекта. При ошибке доступна повторная отправка из этапов карточки при наличии прав редактирования.

## Планировщик

Это внутренний планировщик приложения, а не Linux crontab. Он проверяет задачи каждые 10 секунд; backend должен работать постоянно. Расписание, последний запуск и его результат хранятся в PostgreSQL.

Для синхронизации магазинов по умолчанию задано `0 0 * * *`; часовой пояс — `SCHEDULER_TIMEZONE`, по умолчанию `Europe/Moscow`. Изменить расписание или отключить задачу можно в `/settings/scheduler`.

Cron состоит из пяти полей: `минута час день-месяца месяц день-недели`.

| Пример | Значение |
|---|---|
| `0 0 * * *` | Ежедневно в 00:00 |
| `30 8 * * 1-5` | По будням в 08:30 |
| `*/15 * * * *` | Каждые 15 минут |
| `0 6 1 * *` | Первого числа месяца в 06:00 |

## Эксплуатация

```bash
# Обновить приложение и применить новые миграции
docker compose up --build -d

# Пересобрать только интерфейс без перезапуска API
docker compose up --build -d --no-deps frontend

# Состояние контейнеров и логи
docker compose ps
docker compose logs --tail=100 backend
docker compose logs -f frontend backend

# Остановка / запуск
docker compose down
docker compose up -d
```

Обычный `restart backend` не применяет миграции: их выполняет отдельный сервис `migrate`. Для изменения `.env` пересоздавайте контейнеры через `docker compose up -d`, а не только `restart`.

### Резервное копирование

Используйте `pg_dump` с PostgreSQL-сервера либо с машины, где установлены PostgreSQL client tools:

```bash
pg_dump -h <DB_HOST> -p <DB_PORT> -U <DB_USER> -d <DB_NAME> -Fc -f backup.dump
pg_restore -h <DB_HOST> -p <DB_PORT> -U <DB_USER> -d <EMPTY_DATABASE> --no-owner backup.dump
```

Для пароля используйте запрос клиента или `.pgpass`. Восстанавливайте в подготовленную пустую базу. Отдельно сохраните `.env`, особенно ключ шифрования; не включайте секреты в Git.

### Полная очистка

`cleanup-db.sql` удаляет все 13 таблиц приложения, историю миграций и связанную функцию защиты аудита. Посторонние таблицы схемы `public` не удаляются явно.

Проверка конфигурации без очистки:

```bash
./cleanup-db.sh --check
```

Полный сброс:

```bash
./cleanup-db.sh
# Подтвердите вводом DELETE.
docker compose up -d --force-recreate migrate backend frontend
```

Скрипт останавливает приложение и выполняет SQL через сервис `migrate`. Полный сброс удаляет данные без возможности отмены; предварительно сделайте резервную копию. После него потребуется первичная настройка администратора и интеграций.

## Разработка и проверки

Структура проекта:

```text
src/                  Интерфейс, страницы, компоненты, Zustand
src/config/           Каталог разрешений и зависимости загрузки страниц
src/hooks/            Загрузка данных разделов
backend/src/modules/  Модули API и фоновые задачи
backend/prisma/       Схема, миграции и seed
nginx/                Reverse proxy и раздача frontend
tests/               Проверки интерфейса
backend/tests/        Проверки API, прав, аудита и SD
```

Frontend локально:

```bash
npm ci
npm run typecheck
npm run build
npm run dev
```

Для локального интерфейса отдельно обеспечьте доступ к API; производственный маршрут `/api` проксирует Nginx.

Проверки frontend после установки зависимостей:

```bash
node tests/permissions.cjs
node tests/profile-workflow.cjs
node tests/audit-errors.cjs
```

Проверки собранного backend через Docker:

```bash
docker compose build backend
docker compose run --rm --no-deps -T backend node < backend/tests/permissions.cjs
docker compose run --rm --no-deps -T backend node < backend/tests/profile-workflow.cjs
docker compose run --rm --no-deps -T backend node < backend/tests/audit-errors.cjs
```

Эти проверки используют имитации зависимостей: не создают реальные заявки SD и не изменяют рабочие данные.

## Диагностика

- Ошибка запуска API: проверьте логи `migrate` и `backend`, доступность PostgreSQL и длину `JWT_SECRET`.
- Ошибка LDAP или интеграций после переноса: проверьте сохранность `LDAP_ENCRYPTION_KEY`.
- Справочник магазинов не обновляется: проверьте параметры `UKM_SQL_*`, доступ к SQL Server и результат задачи планировщика.
- Уведомление не отправлено: проверьте включение интеграции, правило, время по Москве, дату события и причину ошибки в аудите.
- Нет доступа к разделу или действию: проверьте просмотр и нужное действие в назначенной роли.
