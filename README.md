# Реконструкция — Закрытие

Система управления графиками реконструкций, закрытий и открытий магазинов.

## 🚀 Быстрый старт

### Требования
- Docker 20.10+
- Docker Compose 2.0+
- PostgreSQL 13+ (внешняя база данных)

### 1. Настройка

```bash
# Скопируйте пример конфигурации
cp .env.example .env

# Отредактируйте .env
nano .env
```

Укажите настройки PostgreSQL:
```env
DB_HOST=your-postgres-host
DB_PORT=5432
DB_NAME=store_reconstruction
DB_USER=postgres
DB_PASSWORD=your_secure_password
JWT_SECRET=<сгенерируйте случайный секрет не короче 32 символов>
JWT_EXPIRES_IN=15m
DOMAIN=https://your-domain.example
```

### 2. Создание базы данных

```bash
psql -h $DB_HOST -p $DB_PORT -U $DB_USER -c "CREATE DATABASE $DB_NAME;"
```

### 3. Запуск

```bash
docker compose up --build -d
```

### 4. Доступ

- **Frontend**: http://your-server-ip:5001
- **Backend API**: доступен через reverse proxy по адресу http://your-server-ip:5001/api
- **Swagger**: http://your-server-ip:5001/api/docs
- Порт 4000 backend не публикуется на хост

### 5. Первичная настройка администратора

Система **не содержит стандартных логинов и паролей**. Для первого запуска:

1. Сгенерируйте секрет: `openssl rand -base64 48` и задайте полученное значение в `JWT_SECRET`.
2. Временно задайте в `.env` `BOOTSTRAP_ADMIN_PASSWORD` со случайным паролем длиной не менее 12 символов.
3. Запустите `docker compose up --build -d`. Сервис `migrate` применит миграции и создаст администратора.
4. Удалите `BOOTSTRAP_ADMIN_PASSWORD` из `.env` и выполните `docker compose run --rm migrate`, чтобы больше не хранить пароль первичной настройки в конфигурации.
5. Для дальнейших пользователей используйте раздел управления пользователями.

Не публикуйте `.env` и не используйте тестовые пароли в production.

## 🗄 Резервное копирование

```bash
# Создать бэкап
pg_dump -h $DB_HOST -p $DB_PORT -U $DB_USER $DB_NAME > backup_$(date +%Y%m%d).sql

# Восстановить
psql -h $DB_HOST -p $DB_PORT -U $DB_USER -d $DB_NAME < backup.sql
```

## 🏬 Справочник магазинов и планировщик

Справочник хранится в PostgreSQL и синхронизируется из SQL Server представления Ukm_Data.dbo.v_1C_Shops_Info. Новые магазины добавляются, существующие обновляются только при изменении данных; отсутствующие в источнике записи не удаляются.

Добавьте в корневой .env параметры UKM_SQL_SERVER, UKM_SQL_PORT, UKM_SQL_DATABASE, UKM_SQL_USER, UKM_SQL_PASSWORD и при необходимости UKM_SQL_VIEW. Указанные секреты передаются только backend-контейнеру. Образ backend включает Python 3 и Microsoft ODBC Driver for SQL Server для подключения через pyodbc.

После пересборки и запуска миграций откройте «Справочник → Магазины» и нажмите «Синхронизировать сейчас». В разделе «Настройки → Планировщик (crontab)» по умолчанию включена задача ежедневной синхронизации в 00:00 по часовому поясу сервера; задачу можно отключить или изменить пятичастное cron-выражение. В форме добавления объекта номер используется для поиска в справочнике, а адрес заполняется автоматически и доступен только для чтения.


### Cron-выражения

Планировщик приложения проверяет включённые задачи раз в 30 секунд. Сейчас зарегистрирована задача синхронизации справочника магазинов; расписание и результат хранятся в PostgreSQL. Это внутренний планировщик приложения, а не запись в системном Linux crontab. Для автоматического выполнения backend должен быть постоянно запущен.

Cron задаётся пятью полями: `минута час день-месяца месяц день-недели`.

| Пример | Значение |
|---|---|
| `0 0 * * *` | Каждый день в 00:00 |
| `30 8 * * 1-5` | По будням в 08:30 |
| `*/15 * * * *` | Каждые 15 минут |
| `0 6 1 * *` | Первого числа каждого месяца в 06:00 |

Используется часовой пояс backend-сервера. В настройках роли права на просмотр страницы магазинов (`view_shops`) и синхронизацию (`manage_shops`) назначаются отдельно. Поле адреса в форме объекта заполняется по номеру магазина из справочника; поиск адреса доступен авторизованным пользователям, которым разрешено работать с объектами.

### Автоматический выход

Frontend завершает локальную сессию по времени `exp` в JWT. Сервер также проверяет срок действия токена при каждом защищённом запросе. Значение срока задаётся переменной `JWT_EXPIRES_IN` (например, `15m`, `1h`).
